This plan describes **how** spec 003 will be built. It doesn't change **what** the spec asks for. If something here contradicts the spec, the spec wins and this plan gets fixed.

---

## 1. Approach in one paragraph

Add a **Playwright** suite in `e2e/`, run against a production build of the app (`next build` + `next start`) and a **throwaway PostgreSQL started inside the CI job**, reached through a small proxy that speaks the Neon HTTP protocol, so the app uses **the same database driver as in production** and CI holds **no secret at all** (D-1). Tests sign in with a session created by **Better Auth's own `testUtils` helpers**, from a test-only auth instance that lives in `e2e/` and is never imported by the app (OQ-1). Every test starts from an empty task table, runs one at a time, and builds its dates from "now in Toronto" with the existing `src/domain/local-date.ts`. An **axe** scan runs inside the same suite and fails on any violation. The README is rewritten twice: the text on day 1, then screenshots (generated by Playwright from the same fake data) and the traceability example at the end. Four slices, one PR each (spec OQ-5).

## 3. CI database (D-1)

**Problem.** The app talks to Neon with the HTTP driver (`drizzle-orm/neon-http`). A plain PostgreSQL container in GitHub Actions does not speak that protocol.

**Recommended design (D-1 option A).** Two containers in the CI job, as in Neon's own guide for local development:

| Container | Image | Role |
|---|---|---|
| `postgres` | `postgres:17` | The throwaway database. Created at the start of the job, gone at the end. Fake data only. |
| `neon-proxy` | `ghcr.io/timowilhelm/local-neon-http-proxy`, **pinned by digest** | Receives the driver's HTTP queries on port 4444 and forwards them to `postgres`. |

- The app's `DATABASE_URL` in CI is `postgres://postgres:postgres@db.localtest.me:5432/main`. `db.localtest.me` points to 127.0.0.1; the workflow also writes it to `/etc/hosts` so the job doesn't depend on outside DNS.
- `src/server/db/client.ts` gets one rule: **if the host is `db.localtest.me`**, send the driver's queries to `http://db.localtest.me:4444/sql`. Every other host (production, `dev`: `*.neon.tech`) is unchanged. This is safe by construction: the production URL can never match.
- **Migrations** run with Drizzle's `neon-http` migrator from the committed `drizzle/` files, through the same proxy. The test database gets exactly the schema production gets, by the same driver. (Not `drizzle-kit`: it picks its driver from installed packages, and adding one could change how Vercel migrates production.)
- The same `docker-compose.e2e.yml` runs it on a laptop (`npm run e2e:db`), so the suite can be run locally. Docker is already installed on the PO's Mac.
- **Secrets: none.** `BETTER_AUTH_SECRET` is generated fresh for each run (`openssl rand`); `ALLOWED_EMAILS=owner@example.com`; the Google client id and secret are dummy strings (Google is never called). TR-2 holds by construction.

Options considered are in §9 D-1.

## 4. Signing in, in tests (spec OQ-1 → option A)

Better Auth 1.7 ships an official **`testUtils`** plugin for this exact need. Its own documentation says to keep it in a **separate, test-only auth instance**, not in the production config. That's what this plan does:

```
e2e/support/test-auth.ts
  betterAuth({ database: <test DB>, secret, baseURL: same as the app, plugins: [testUtils()] })
```

1. **Global setup** (once per run): migrate, then with `ctx.test`: create `owner@example.com` (in `ALLOWED_EMAILS`) and `stranger@example.com` (not in it); `getCookies()` for each → saved as Playwright "storage state" files in `e2e/.auth/` (git-ignored).
2. Tests use the owner's storage state by default; `access.spec.ts` also uses none and the stranger's.
3. The app then does exactly what it does in production: the proxy sees a cookie, the page calls `requireAllowedSession()`, Better Auth reads the session from the database, the allowlist is checked.

**What this proves and what it doesn't** (goes in the README, spec AC-4.3):

| Proved automatically | Not automated, on purpose |
|---|---|
| A signed-out visitor is sent to `/sign-in` and sees the Google button | The redirect to Google and back (UAT, every 90 days in real use) |
| A valid session with an allowed email sees the tasks | That Google refuses accounts that aren't test users (ADR-0012; Google's side) |
| A valid session whose email is **not** (or no longer) allowed is refused: no task shown | The hook that refuses to *create* a session for a stranger at sign-in (spec 001 AC-3.1): covered by its unit test and UAT |

**TR-3 enforcement:** `e2e/` is outside `src/` and outside the Next.js build. A new ESLint rule refuses any import of `e2e/**` or of `testUtils` from `src/`. `e2e/support/env.ts` throws if the database host is not `db.localtest.me`, so the test auth instance cannot even start against `dev` or production.

## 5. Key design points

### 5.1 Isolation and order (AC-1.6)

Tasks have **no owner column**: the app is single-user by design (vision §3), so tests can't be isolated by giving each one its own user. Instead:

- **One test at a time** (`workers: 1`).
- Before each test, a fixture empties `task` and `usage_day` (sessions and users stay).
- Each test seeds exactly the tasks it needs, directly in the database. Adding through the UI is tested once, in `add-task.spec.ts`; other tests don't depend on it.

With ~20 tests of a few seconds each, one worker stays well within the 5-minute target (AC-1.7). If the suite grows past it, sharding is the next step, not shared state.

### 5.2 Time (AC-1.5)

- Test data is built from `localNow(new Date())` and `addDays()` from `src/domain/local-date.ts` (pure, so it can be imported by tests). "Overdue" = yesterday; "overdue timed" = today at 00:00; "soon" = today and tomorrow; "later" = +7 days.
- **Midnight guard:** if a test starts within 2 minutes of midnight Toronto time, the fixture waits until 00:02 before seeding. Without it, the test and the server could disagree about which day "today" is (a classic flaky test). A CI run at 04:00 UTC (11 p.m. Toronto) is part of UAT.
- The browser's time zone is set to `America/Toronto` in the config, so nothing depends on the CI machine's zone (UTC).

### 5.3 Finding elements (TR-4)

By role, label and visible text, which the app already provides: `checkbox` "Mark "…" done", `button` "Edit "…"", `region` "Tasks", `status` for the undo bar, `alert` for errors. No CSS selector.

### 5.4 Checking colours (AC-2.3 to AC-2.6)

Asserting a computed colour ties the test to Tailwind's palette. Instead, the due label gets a **`data-urgency="overdue|soon|none"`** attribute set from the same `urgency()` value that picks the colour. The tests check the attribute **and** the visible text label (AC-2.6). The axe scan checks the colour contrast itself. This is a markup addition, not a behaviour change (spec §5).

### 5.5 Browsers and viewports (AC-1.4)

| Project | Device | Runs |
|---|---|---|
| `desktop` | Desktop Chrome | every test |
| `phone` | Pixel 7 profile (Chromium, 412 px wide, touch) | tests tagged `@phone`: add, done + undo, accessibility |
| `screenshots` | phone + desktop, light + dark | only by `npm run screenshots` |

Playwright's iPhone profiles use WebKit, which is out of scope (spec §5); the real iPhone stays in UAT.

### 5.6 Accessibility (US-6)

`@axe-core/playwright` with tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`. Scanned states: sign-in page; home with a mixed list (red, amber, none); home empty; edit view open; undo bar showing. In both `desktop` and `phone`, light and dark colour scheme. **Any violation fails the test**, with the axe report attached. The first run's findings are listed in `tasks.md` and fixed (AC-6.3).

### 5.7 Failures and flakiness (US-2)

- `trace: "retain-on-failure"`, `screenshot: "only-on-failure"`; the HTML report and `test-results/` are uploaded as a CI artifact when the job fails (kept 7 days). Fake data only, so the artifact is safe in a public repo.
- `retries: 1` in CI so a flaky test is **detected and named** in the run summary, and `failOnFlakyTests: true` so it **still turns the run red** (ADR-0015: a flaky test is a bug). If the installed Playwright version lacks the option, the JSON report is checked by a short script instead.

### 5.8 CI job

Today the workflow runs on **every push and every pull request**, so a PR branch runs CI twice per push (once for the push, once for the PR). With a 2–5 minute browser job, that doubles the wait for nothing. New triggers: `pull_request` (any branch) and `push` to `main` only.

```
on: pull_request · push to main
jobs:
  check:   (unchanged) Typecheck, lint, test — always runs (~30 s)
  changes: lists the files changed by the PR (plain `git diff`, no third-party action);
           output code=true unless every file is under docs/ or specs/, or is a *.md file
  e2e:     End-to-end tests — needs: changes, if: code == 'true'
    services: postgres, neon-proxy (pinned)
    steps: checkout · setup-node (cache npm) · npm ci · cache + install Playwright Chromium
           · /etc/hosts entry · generate BETTER_AUTH_SECRET · next build · playwright test
           (webServer: next start) · upload report on failure
  screenshots: manual only (workflow_dispatch) → uploads docs/screenshots/*.png as an artifact
```

The new job name must be added to the `main` ruleset's required checks (PO setup, §8): today only "Typecheck, lint, test" is required.

**Why a `changes` job and not GitHub's `paths-ignore` (D-4):** with `paths-ignore`, a docs-only PR never starts the workflow, so a *required* check never reports and the PR is stuck on "Expected — waiting for status". A job skipped by an `if:` condition is reported as **skipped**, which GitHub's required checks accept as passing. The file list errs on the safe side: any file outside `docs/`, `specs/` or `*.md` (even `package.json` or a workflow file) runs the full suite. Pushes to `main` follow the same rule.

### 5.9 Screenshots (AC-3.1 to AC-3.4)

`npm run screenshots` (or the manual CI job) seeds a fixed, realistic-looking fake list (e.g. "Submit lab report", "Dentist", "Call the bank": generic, nothing from the PO's real tasks), then saves `docs/screenshots/tasks-phone-light.png`, `tasks-phone-dark.png`, `tasks-desktop-light.png`, `tasks-desktop-dark.png`, `sign-in.png`. Stable names so the PO's website can link to them. Because dates move, the seed uses relative dues, and the screenshots are regenerated only when the UI changes.

### 5.10 README (US-3 to US-5)

Order, top to bottom: title + one-line pitch + CI badge → screenshots → "Why" (problem in 3 lines) → "How it was built" (cycle diagram in Mermaid, roles, AI transparency) → "How quality is ensured" (the 4 layers of ADR-0015 as a table, and the "not automated on purpose" list) → "Follow one requirement" (worked example: spec 002 **BR-5 overdue** → `src/domain/task.test.ts` → `e2e/list.spec.ts` AC-2.3 → a green CI run) → documentation map → stack → run locally (last, AC-4.5).

## 9. Decisions — resolved by the PO on 2026-11-22

| # | Decision | Options | Recommendation |
|---|---|---|---|
| D-1 ✅ | Where does CI get its throwaway database? | **A. PostgreSQL + Neon HTTP proxy inside the CI job** (§3) · B. A Neon branch per CI run (Neon's GitHub actions) · C. Switch the app to a standard PostgreSQL driver when testing | **Accepted by the PO, 2026-11-22: A.** No secret, nothing in CI can reach production by construction (TR-1, TR-2), and the same driver as production. **B** needs a Neon API key in GitHub: that key can manage — and delete — the `production` branch, which breaks TR-2 and the spirit of ADR-0014. It also needs a branch from `dev` or production as its starting point (copying data in) and uses up the free plan's 10 branches with open PRs. **C** tests a different driver from the one in production, so a driver bug would slip through. Cost of A: a community proxy image (pinned by digest, §10) and a 6-line rule in `client.ts`. |
| D-2 ✅ | Accept **ADR-0015** (unit + focused end-to-end + accessibility + UAT; supersedes ADR-0010)? | Accept · Change the layers | **Accepted by the PO, 2026-11-22.** It writes down what spec 003 already asks for, and adds two rules future specs must follow: each plan says which layer checks each AC; a flaky test is a bug. |
| D-3 ✅ | Should a flaky test (fails, then passes on retry) **turn CI red**? | **A. Yes** (`failOnFlakyTests`) · B. No, only reported in the summary | **Accepted: A.** Matches your "we want this clean": a flaky test that stays green trains everyone to ignore CI. The cost: an occasional red run for a test problem, not an app bug, which then has to be fixed before merging. |
| D-4 ✅ | Skip the end-to-end tests on documentation-only pull requests? *(PO question)* | **A. Yes, with a `changes` job** (§5.8) · B. Yes, with `paths-ignore` · C. No, always run | **Accepted: A.** The PO also asked to fix the double CI run right away: done in the plan's own PR (triggers: PRs + `main`). Common practice, and it keeps planning PRs at ~30 s. B looks simpler but blocks docs-only PRs forever once the job is required. C wastes 2–5 minutes on every spec PR. Needs spec AC-1.1 changed (v1.1, AC-1.1b). |

*QA lesson (D-1):* a test environment is part of the system under test. The question isn't only "does it work", it's "what can it reach if something goes wrong". A CI job with no credentials can't damage production even if a test, a dependency or a workflow is compromised. That's a stronger guarantee than "we were careful with the key".

## 10. Risks

| Risk | Impact | Response |
|---|---|---|
| The community proxy image changes or disappears | CI broken, or a modified image runs in CI | Pinned by digest, so it can't change under us. It only ever sees fake data and no secret. If it disappears: build it from its source in the job, or fall back to D-1 option C for tests only (new decision). |
| The proxy doesn't behave like real Neon for some query | A false failure (or a false pass) | Slice 2 proves it early with migrations + the access tests. Production stays checked by UAT. |
| Better Auth `testUtils` changes in an upgrade | Global setup fails | It fails loudly, at setup, before any test runs. The plugin is official and documented. |
| First axe scan finds many issues | Time box (spec AC-6.3) | Scan runs in slice 3, early in the week; list first, estimate, stop and ask if over budget |
| Midnight or daylight-saving edge cases make tests flaky | False reds | Midnight guard (§5.2); dates relative to Toronto "now"; D-3 makes any flake visible right away |
| CI time grows past 5 minutes | AC-1.7 | Chromium only; Playwright browsers cached; phone project limited to `@phone` tests |
| Time box (2026-12-06) runs short | M5 not met | Slice order puts the README first; "cut from the end" rule — screenshots and the worked example can ship after the flows if needed |

This plan describes **how** spec 001 will be built. It doesn't change **what** the spec asks for. If something here contradicts the spec, the spec wins and this plan gets fixed.

---

## 1. Approach in one paragraph

Create a Next.js (TypeScript) app with a framework-free `domain/` folder for business rules. Deploy it to Vercel on day one, even empty, then add the Neon database, then Google sign-in through Better Auth with the allowlist. **Test sign-in from the installed iPhone app as soon as it works (OQ-3)**, then add usage days and the home line. CI runs from the first commit with code.

```
│   │   ├── (app)/layout.tsx       # guard: session required, records usage day
│   │   ├── (app)/page.tsx         # placeholder home + "Used N of the last 7 days"
│   │   └── api/auth/[...all]/     # Better Auth endpoints
│   ├── domain/                    # pure TypeScript — NO Next.js, NO database
│   │   ├── allowlist.ts (+ .test.ts)
│   │   ├── local-date.ts (+ .test.ts)
│   │   └── usage.ts (+ .test.ts)
│   └── server/                    # glue: auth config, database, repositories
│       ├── auth.ts
│       ├── db/schema.ts
│       ├── db/client.ts
│       └── usage-repository.ts

└── README.md
```

**Rule:** `domain/` imports nothing from `app/` or `server/`. That's what keeps business rules testable in milliseconds.

## 3. Business rules → domain functions and tests

Each business rule from the spec gets one function and its tests.

| Rule | Function (in `domain/`) | Example tests |
|---|---|---|
| BR-1 Allowlist | `isAllowed(email, allowlist)` | exact match → true; `" Me@Gmail.com "` vs `me@gmail.com` → true; unknown → false; empty allowlist → false |
| BR-2 Local "today" | `localDate(instant, "America/Toronto")` → `"YYYY-MM-DD"` | **Saturday 23:30 Toronto = Sunday 04:30 UTC → Saturday** (AC-5.3); daylight-saving switch days |
| BR-3 One usage day per date | enforced by the database (primary key on `day`) + "insert if not exists" | covered by the repository; idempotent insert |
| BR-4 Last 7 days | `countUsedLastNDays(days, today, 7)` | today included; day 7 back excluded; empty → 0; duplicates impossible |

No date library: the built-in `Intl.DateTimeFormat` handles time zones correctly.

## 4. Data model for this spec

| Table | Columns | Note |
|---|---|---|
| `user`, `session`, `account`, `verification` | Generated by Better Auth | Sessions stored in the database |
| `usage_day` | `day DATE PRIMARY KEY` | One row per local date. No `user_id`: single-user app (vision §3). |

The schema is defined in TypeScript with Drizzle. Each change generates a SQL migration file that is committed and reviewed like code.

## 5. Key design points

### 5.1 Private access (US-2, US-3) — defense in depth

1. **At sign-in:** a Better Auth hook refuses to create a user or session when `isAllowed` is false. The sign-in page then shows "This app is private." (AC-3.1)
2. **On every server entry point:** the `(app)` layout and every server action check that a session exists **and** that its email is still allowed (AC-3.2). Removing an email from `ALLOWED_EMAILS` locks it out on the next request.
3. **Optimistic redirect:** an unauthenticated visit to any page goes to `/sign-in` (AC-2.1). This step is for UX only; real security is points 1 and 2.

### 5.2 Long session (US-4)

Session lifetime of **90 days, extended on use** (renewed at most once a day). Secure, HTTP-only cookie. "Sign out" deletes the session (AC-4.2).

### 5.3 iPhone sign-in from the installed app (OQ-3, AC-2.3) — the main risk

- The manifest uses `display: "standalone"`, with `start_url` and `scope` = `/`.
- Sign-in uses a full-page redirect to Google and back. No popup, since popups are what usually breaks in installed apps.
- **Spike right after auth is deployed:** install on the iPhone, sign in from the icon, then close and reopen the app.
- **If it fails** (the session ends up in Safari instead of the app), stop and come back to the PO with options before building anything else. There is no workaround decided in advance.

### 5.4 Recording usage days reliably (US-5) — a trap found while planning

An installed iPhone app often **resumes from the background without reloading**. If the usage day is recorded only on page load, opening the app in the morning after using it the night before may record **nothing**. So the usage day is recorded in two places:
1. On page load, in the `(app)` layout (server side).
2. **When the app becomes visible again** (browser `visibilitychange` event), with a small server call that records today and refreshes the "Used N of 7" line.

Both use "insert if not exists", so repeated calls are harmless (BR-3).

### 5.5 Speed (AC-NF-1)

- The home page renders on the server with a single small query. No heavy JavaScript.
- The Neon database is created in **AWS us-east-1** and Vercel functions run in **iad1** (Washington), so the app and the database are next to each other.
- Neon Free sleeps after **5 minutes** idle. The first query after sleeping is slower, and the cold-start measurement in UAT shows by how much.

### 5.6 Secrets and environments (NFR-06)

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Neon connection (dev branch locally, main branch in production) |
| `BETTER_AUTH_SECRET` | Signs sessions (random, generated once per environment) |
| `BETTER_AUTH_URL` | App base URL (`http://localhost:3000` / production URL) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google OAuth client |
| `ALLOWED_EMAILS` | Comma-separated allowlist |

`.env` is git-ignored. `.env.example` lists the names with no values.

### 5.7 Database migrations

Vercel's build runs the migrations before building, against **that environment's** database. Production uses the Neon `main` branch; previews and local use `dev`. A bad migration therefore fails the deployment instead of breaking the live app halfway.

### 5.8 CI and branch flow (US-6)

- **Workflow:** work on a branch → pull request → CI must be green → merge to `main` → Vercel deploys to production.
- **CI (GitHub Actions, Node 24 LTS):** `npm ci` → typecheck → ESLint → Vitest.
- **Branch protection on `main`:** CI required, no direct push. This is what makes AC-6.2 true.

## 7. Order of work (preview of tasks.md)

1. Scaffold the Next.js app, `domain/` with BR-1, BR-2, BR-4 and their tests, CI workflow, README, `.env.example`.
2. **PO setup:** Vercel. Then: deploy the empty app, PWA manifest and icons → check AC-1 on the iPhone.
3. **PO setup:** Neon. Then: Drizzle, `usage_day` table, migrations in the build.
4. **PO setup:** Google Cloud. Then: Better Auth, allowlist hook, guards, sign-in and sign-out pages.
5. **iPhone sign-in spike (§5.3).** Go / no-go.
6. Usage days: recording on load and on resume, "Used N of the last 7 days" line.
7. **PO setup:** branch protection. Final pass, then **PO UAT** using the spec's checklist.
